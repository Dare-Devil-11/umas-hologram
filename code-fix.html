Step 1 of 60% complete
01
Read the Code
Before you touch anything — understand exactly what is broken and where. Read the file, find the line, copy the block.
Step 1 of 6
✓
Identify the file and exact line number
Open the file. Find the function or block that is broken. Note the line numbers.
How to find it
Look at the error message first — it usually gives you a file path and line number. If not, search for the function name or the error text inside the codebase.
grep -rn "error_text_here" . --include="*.js" --include="*.py" --include="*.ts"
grep -n "function_name" path/to/file.js
Claude Prompt
Read [filename] and tell me what line the [function/error] is on and what that block is supposed to do.
✓
Read the full function — not just the error line
Read 20+ lines above and below the error. The bug is often not on the exact line the error points to.
Why this matters
Error messages lie about location. A null pointer on line 47 was caused by a missing assignment on line 12. Read the whole function before deciding what to change.
sed -n '30,70p' path/to/file.js
Claude Prompt
Read lines [N-20] to [N+30] of [filename]. Tell me what the function does and what could cause [error message].
✓
Copy the broken block to your notes
Paste the broken code somewhere. You need the original to compare against your fix later.
Before you change anything
Git stage or stash your current state. If you have no git, copy the file to filename.backup. You will need to compare original vs fixed.
git diff HEAD
cp path/to/file.js path/to/file.js.backup
✓
Write down what the code IS doing vs what it SHOULD do
In plain English. One sentence each. This is your problem statement. You need this for step 2.
Example format
IS doing: "Returns undefined when user is not logged in"
SHOULD do: "Returns an empty object {} when user is not logged in"

If you cannot write this in one sentence — you have not read the code enough. Go back and read more.
02
Research the Code
Understand WHY it broke. Search the error. Check the docs. Find working examples before writing a single line.
Step 2 of 6
✓
Search the exact error message
Copy the full error text. Search it in quotes. The first 3 results usually contain the answer.
Search strategy
1. Copy the error message exactly
2. Remove file-specific parts (line numbers, variable names)
3. Search: "exact error message" + language/framework name
4. Filter to last 2 years on Stack Overflow
Claude Prompt
I'm getting this error: [paste full error]. The code is in [language/framework]. Explain what causes this error and the most common fix.
✓
Check the official docs for the function being called
The function signature may have changed. Parameters may have been renamed or reordered in a newer version.
Version mismatch is the #1 cause of "worked before, broken now"
Check your package version: run npm list [package] or pip show [package]. Then check the changelog for breaking changes between your version and the latest.
npm list --depth=0
pip show package-name
Claude Prompt
Look up the docs for [function name] in [library v.X]. What are the required parameters and return type? Has the API changed in recent versions?
✓
Find 2 working examples of the correct pattern
Find real code that does the same thing correctly. Use GitHub search, docs examples, or Stack Overflow accepted answers.
GitHub code search (most underused resource)
Search GitHub for the exact function call in real repos. Example: search language:python "requests.get" "timeout=" to find real usage patterns. Filter to repos with 100+ stars for quality signal.
Claude Prompt
Show me 2 correct working examples of [what you're trying to do] in [language/framework]. The examples must handle [specific edge case].
✓
Confirm root cause — not just symptom
The error message is a symptom. What is the actual root cause? Write it down before moving forward.
5 Whys technique
Ask "why" 5 times:
Why did it fail? → null value
Why was it null? → function returned early
Why did it return early? → missing guard clause
Why missing? → new API version removed default
Root cause: version upgrade broke assumption.

Fix the root cause, not the symptom.
Claude Prompt
Given this broken code: [paste code] and this error: [paste error], what is the ROOT CAUSE — not just the symptom? Use 5 Whys reasoning.
03
Find the Replacement
Write the correct version of the broken code BEFORE touching the file. Know exactly what you are putting in before you take anything out.
Step 3 of 6
✓
Write the corrected code block in isolation
Write the replacement in a scratch file or notes — not in the original yet. Get it right before you put it in.
Draft it first
Open a new file: scratch.js / scratch.py. Write ONLY the fixed function or block. Don't touch the original file until you are confident in the replacement.
Claude Prompt
Here is the broken code: [paste it]. The root cause is [root cause]. Write me the corrected version. Only change what is necessary to fix the problem. Do not refactor anything else.
✓
Verify the replacement matches the required function signature
Input types, output type, parameter names — must match what the callers expect. Don't change the interface.
Check callers before changing the signature
Search for everywhere the function is called before changing its parameters. If the function takes (userId, options) and you change it to (options, userId) — every caller breaks silently.
grep -rn "functionName(" . --include="*.js" --include="*.ts"
Claude Prompt
Here is my replacement: [paste it]. Here is how it is called in the codebase: [paste caller code]. Does my replacement break any of the callers? What would need to change?
✓
Diff: list every line that changes
Before applying: write out ORIGINAL LINE → NEW LINE for each change. If you cannot list the exact changes — you do not have a replacement yet.
Smallest change wins
The fix should touch the minimum number of lines. If your fix changes 15 lines when the bug was on 2 lines — you are doing too much. Break it down. Fix one thing at a time.
Claude Prompt
Show me ONLY the lines that need to change to fix this. Format as: OLD: [line] → NEW: [line]. Do not show unchanged lines.
04
Make the Edits
Apply exactly what you drafted in step 3. Nothing more. No "while I'm in here" changes. Surgical only.
Step 4 of 6
✓
Backup / git stash the current state
Stage your current working state before making changes. You must be able to revert in one command.
Always have an undo
Never edit without a rollback path. Git stash or commit before you change anything. No exceptions.
git add -A && git stash
git add -A && git commit -m "chore: snapshot before fix"
✓
Apply ONLY the changes from your diff list
Change line by line. Do not add comments, do not clean up nearby code, do not rename anything else. One fix, one change.
Discipline prevents new bugs
Every "while I'm in here" change is a new bug waiting to happen. If you notice something else broken — write it down for the next run through this pipeline. Fix one thing at a time.
Claude Prompt
Edit [filename]. Apply ONLY these changes: [paste your diff list]. Do not change anything else. Do not clean up nearby code.
✓
Verify the diff after editing
Run git diff. Confirm ONLY the lines you intended to change are different. If extra lines changed — undo and redo.
Check before you run
Reading the diff before testing catches copy-paste errors, whitespace-only changes that look invisible, and accidental deletions before they waste your test cycle.
git diff
git diff --stat
05
Test the Edit
Run it. Check the original error is gone. Check you didn't break anything else. Document the result.
Step 5 of 6
✓
Run the code — confirm original error is gone
Run the exact same flow that triggered the original error. If the original error is still there — the edit didn't fix the root cause. Go back to step 2.
Reproduce the original bug first
Run the same test case that originally showed the bug. Not a different test — the same one. If it passes, move on. If same error: return to step 2, root cause was wrong.
npm test
python -m pytest tests/ -v
node path/to/file.js
✓
Test the 3 edge cases around the fix
What happens with: (1) empty/null input, (2) the normal case, (3) the extreme case. All 3 must pass.
Edge cases that always bite
For any fix, test:
• Empty string / null / undefined input
• Single item vs array of items
• Async timing (what if it takes 0ms? 5000ms?)
• User is not logged in / session expired
• The function called twice in a row
Claude Prompt
Here is my fix: [paste fixed code]. What are the 3 most likely edge cases that could still break this? Write me a test for each one.
✓
Check that nothing else broke (regression test)
Run the full test suite or manually test the 2 features most likely to be affected by your change.
Find regression risk with grep
Search for everywhere the function you changed is called. Manually test each caller. A fix that breaks 3 other things is not a fix — it is a new set of bugs.
npm run test:all 2>&1 | grep -E "FAIL|PASS|ERROR"
Claude Prompt
I changed [function name] in [file]. Search the codebase for all callers of this function and tell me which ones might be affected by [description of change].
✓
Return the Output
Fix confirmed. Document what you did, commit the change, log the solution so you never debug this again.
Step 6 of 6
✓
Commit the fix with a clear message
Commit message must say: what broke, what the fix was, why. Future you will thank you.
Good commit message format
fix: [what was broken] — [root cause] → [what changed]

Example: "fix: login returning null on missing session — getUser() returned undefined instead of {} when session expired → added null guard with default return value"
git add -A && git commit -m "fix: [what broke] — [root cause] → [what changed]"
✓
Log the fix to error-log.md
Append the error, root cause, and fix to ~/AI-OS/logs/error-log.md. Search {keyword} next time instead of debugging from scratch.
Log format
---
TIME: [date]
ERROR: [error message]
ROOT CAUSE: [why it happened]
FIX: [what you changed]
FILE: [filename:line]
STATUS: RESOLVED
---
Claude Prompt
Append to ~/AI-OS/logs/error-log.md: ERROR: [error], ROOT CAUSE: [cause], FIX: [fix], FILE: [file], STATUS: RESOLVED
✓
Write the final output summary
One paragraph: what was broken, what you changed, what it does now. This is what you hand off or report.
Claude Prompt
Summarize this fix in 3 sentences: the bug was [describe], caused by [root cause], fixed by [change made]. Output is now [expected behavior].
